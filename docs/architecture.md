# Software Architecture

## Overview

The firmware runs bare metal on the STM32F446RE without an operating system.
`main()` initializes the hardware and then runs a superloop that calls the access controller in every iteration.
The modules store start times and check elapsed time instead of waiting. Only display updates (about 0.1 s with text) and log output block the loop for a short time.

```text
main.c            init, superloop
   │
   ▼
Application       access_controller.c   state machine, decisions, fault handling
   │
   ▼
Device drivers    rfid.c      MFRC522 RFID reader (SPI)
                  oled.c      SSD1306 display (I²C), chars.c: character bitmaps
                  servo.c     MG90S servo (PWM), lock/unlock timers
                  sensors.c   bolt and door sensors (GPIO), debouncing
                  uart.c      UART output (register level, no HAL)
                  log.c       log messages with timestamp
   │
   ▼
HAL / CMSIS       STM32 peripherals (SPI, I²C, TIM, GPIO), registers
   │
   ▼
Hardware          STM32F446RE, MFRC522, SSD1306, MG90S, switches
```

## Own code and generated code

| Part | Files | Origin |
| --- | --- | --- |
| Application and device drivers | `access_controller.*`, `rfid.*`, `oled.*`, `chars.*`, `servo.*`, `sensors.*`, `uart.*`, `log.*` | own code |
| Initialization of clocks and peripherals | `main.c` (outside the `USER CODE` blocks), `stm32f4xx_hal_msp.c`, `stm32f4xx_it.c` | generated by STM32CubeMX |
| RFID interrupt setup and superloop | `main.c` (`USER CODE` blocks), `EXTI2_IRQHandler` in `stm32f4xx_it.c` | own code in generated files |
| HAL, CMSIS, startup code, linker script | `Drivers/`, `startup_stm32f446xx.s`, `STM32F446XX_FLASH.ld` | ST |
| Character bitmaps for the display | `chars.c` | created with AI help after the first characters were done by hand |

## Startup

1. CubeMX initialization (clock 84 MHz, GPIO, TIM2, SPI2, I²C1)
2. RFID interrupt on PC2 (EXTI2, falling edge)
3. UART initialization
4. Start of the servo PWM; on failure: error log and `Error_Handler()`
5. Display initialization; on failure: warning log, continue without display
6. RFID reader initialization; on failure: FAULT
7. Superloop: in UNINITIALIZED the initial state is chosen from the debounced sensors, afterwards `ACCESS_CONTROLLER_Run()` is called

## State machine

| State | Meaning | Leaves to |
| --- | --- | --- |
| UNINITIALIZED | startup, sensors not yet debounced | initial state from the sensors ([requirements](requirements.md), 4.1) |
| LOCKED_READY | locked, waiting for a card | UNLOCKING (authorized card), LOCKED_BLOCKED (3 unauthorized cards) |
| LOCKED_BLOCKED | access attempts blocked | LOCKED_READY after the block interval |
| UNLOCKING | servo moves the bolt back | UNLOCKED_DOOR_CLOSED (bolt unlocked), FAULT (timeout 500 ms) |
| UNLOCKED_DOOR_CLOSED | unlocked, door closed | UNLOCKED_DOOR_OPEN (door opened), LOCKING (after 30 s) |
| UNLOCKED_DOOR_OPEN | unlocked, door open | LOCKING (door closed) |
| LOCKING | servo moves the bolt out | LOCKED_READY (bolt locked, door closed), UNLOCKING (door opened), FAULT (timeout 500 ms) |
| FAULT | error, servo stopped | only by reset |

In every state, contradictory bolt sensors lead to FAULT.

Transitions are made in one function, `ChangeState()`. It performs the actions of the new state (servo, timers, block counter), logs the new state and updates the display.
FAULT is entered only through `HandleFault()`.

## RFID reading

`MFRC522_DetectUID()` is a non-blocking step function. Each call performs one step of the ISO/IEC 14443-A sequence:

```text
REQA → ATQA → Anticollision CL1 → 4 UID bytes + BCC → check BCC
```

The answer of the card is signalled by the reader's IRQ pin (PC2, EXTI2). The interrupt handler only advances the driver state; SPI accesses are done in the main loop.

| Return value | Meaning | Reaction of the access controller |
| --- | --- | --- |
| `MFRC522_OK` | attempt in progress | call again in the next loop |
| `MFRC522_NO_UID_DETECTED` | attempt finished, no valid card | wait 100 ms, then start the next attempt |
| `MFRC522_UID_DETECTED` | attempt finished, UID read | check the whitelist |
| any other value | communication error with the reader | FAULT |

Disturbed card responses (wrong length, wrong checksum) are handled inside the driver as "no valid card". The detailed reason is stored and can be read with `MFRC522_GetLastError()`.

## Error handling

- Drivers return status codes; success is always `…_OK`, callers check for `!= …_OK`.
- Ignored return values are marked with `(void)`.
- Errors are detected where they occur and handled in `HandleFault()`: stop the servo, store the cause, log it, show "ERROR".
- FAULT is latched until reset.
- The display is optional; its errors are ignored.

The complete list of errors is in the [requirements](requirements.md), 4.6.

## Logging

All modules log through `LOG_Write()` over UART (115200 baud, 8N1):

```text
[1203 ms] INFO SENSOR: Door closed
[1204 ms] INFO CTRL: New state LOCKED_READY
[8410 ms] INFO RFID: Valid UID detected E7 20 75 33
[8411 ms] INFO CTRL: New state UNLOCKING
[9120 ms] ERROR CTRL: Timeout during unlocking; Servo stopped
```

- **INFO / WARN**: normal events, logged where they happen
- **ERROR**: faults, logged only in `HandleFault()`

## Peripherals

| Function | Peripheral | Settings |
| --- | --- | --- |
| System clock | HSI + PLL | 84 MHz, APB1 42 MHz |
| RFID reader | SPI2 | mode 0, 5.25 MHz, software NSS |
| RFID interrupt | EXTI2 (PC2) | falling edge |
| Display | I2C1 | 100 kHz, address 0x3C |
| Servo | TIM2 channel 3 (PB10) | 50 Hz PWM, 1 µs resolution |
| Log output | USART2 (PA2/PA3) | 115200 baud, 8N1 |
| Sensors | GPIO PC0, PC1, PC3 | internal pull-ups, active low |
